以下是回溯记录，不代表独立架构方已经批准。Claude 应逐条确认、否决或迁移进 `ADR-000`；在此之前实现方不据此编写 SRH 业务代码。

## D-001 固定源码构建而不是使用浮动 latest 镜像
- 日期：2026-08-11
- 背景：交易系统需要可复现二开和收益核账，浮动镜像无法还原具体代码。
- 选择：以 `389d24699479daf102bfa9c22882375ca9ebb07a` 为基线，从本地源码构建。
- 否掉了：直接运行上游 `latest`（版本会漂移，无法可靠回滚或评审 diff）。
- 代价：必须自己维护依赖、迁移和构建；基线会落后上游，需要显式升级。
- 状态：用户确认；待 ADR-000 追认。

## D-002 用旁路新增 SRH 而不是改写旧钱包链
- 日期：2026-08-11
- 背景：旧钱包监控、confluence/copy 和其他市场模块已在运行，钱包事实又存在身份缺口。
- 选择：新事实、新 worker、新事件和新策略旁路；旧 callback、旧表和旧策略语义保持不变。
- 否掉了：直接重写 `wallet_ws_monitor`、`tracked_traders_worker` 或复用旧 rollup 做研究真相。
- 代价：会有一段时间的新旧双链路和额外存储；必须做去重、对账和故障隔离。
- 状态：设计已由用户确认；待 ADR-000 追认。

## D-003 为 SRH 使用独立 WALLET_FLOW 事件
- 日期：2026-08-11
- 背景：现有 `TRADER_ACTIVITY` 同时服务 confluence/copy，改变 payload 或 sweep 会影响旧策略。
- 选择：拟议新增 `WALLET_FLOW`，桥接时 `sweep_missing=False`、`refresh_prices=False`。
- 否掉了：复用 `TRADER_ACTIVITY` 或让 SRH worker 清扫全部 `traders` signals。
- 代价：增加一个事件契约、catalog/loader 注册和独立回归面。
- 状态：待 ADR-000 追认；尚未实现。

## D-004 单独读取完整钱包历史而不改变旧 client 方法
- 日期：2026-08-11
- 背景：Polymarket Data API 的 trades 默认会漏 maker 活动，旧调用方可能依赖现有行为和缓存。
- 选择：拟议增加 SRH 专用完整读取，显式 `takerOnly=false`，保留旧方法不变。
- 否掉了：全局修改 `get_wallet_trades` 默认参数（会改变未知调用方结果与缓存）。
- 代价：短期存在两个近似 client 方法，需要命名、测试和维护边界。
- 状态：待 ADR-000 追认；官方契约需在实现时重新核验。

## D-005 策略不控制 shadow/live
- 日期：2026-08-11
- 背景：同一策略要能由用户在现有系统选择模拟或实盘，且策略层不应持有资金权限。
- 选择：SRH 只输出 Opportunity/ExecutionPlan 参数，继续由 `Trader.mode` 和账户设置决定执行模式。
- 否掉了：在 SRH 配置里增加第二套 live 开关或由 worker 直接调用 CLOB。
- 代价：策略必须适配现有 orchestrator 契约；模式错误仍需依赖现有账户/运行配置防护。
- 状态：用户确认；待 ADR-000 追认。

## D-006 首版不把钱包流注入通用退出内核
- 日期：2026-08-11
- 背景：现有同步 `should_exit` 只接收价格、时间和市场状态，跨进程钱包流不是其契约。
- 选择：首版复用止盈、止损、最大持有、不可交易和结算退出。
- 否掉了：为单一新策略修改所有策略共用的 position lifecycle 输入与 I/O。
- 代价：首版不能按实时钱包流反转退出，可能错过更早止盈或减损。
- 状态：临时方案；待 ADR-000 追认，动态流退出须另立 ADR。

## D-007 新研究事实使用 LOGGED 表和 point-in-time 口径
- 日期：2026-08-11
- 背景：UNLOGGED rollup/signal 可丢失，且事后钱包排名和结算会造成前视污染。
- 选择：拟议新增可对账的 LOGGED 钱包事实/点时特征，并保留 observed/confirmed/as-of 身份。
- 否掉了：把现有聚合快照、当前排行榜或最终结算直接当历史信号真相。
- 代价：增加数据库容量、迁移、保留策略和重算成本。
- 状态：待 ADR-000 追认；属于 schema 变更，ADR 前禁止实施。

## D-008 订单 verification 是收益结论的唯一账本
- 日期：2026-08-11
- 背景：此前模拟界面出现未验证 `$0`、mark-to-market 和实际盈亏混淆，足以误导策略判断。
- 选择：候选 trace 只做解释，收益结论以现有 `TraderOrder` 与 verification 可连接记录为准。
- 否掉了：策略模块自行维护第二套 PnL，或用 expected ROI/理论 payout 代替已核账盈亏。
- 代价：收益反馈晚于候选产生；verification 缺失时只能报告“未证实”，不能给漂亮数字。
- 状态：已确认长期原则；待 ADR-000 形式化。

## D-009 用新的 AGENTS 约定替换旧 clean-cut 规则
- 日期：2026-08-11
- 背景：旧 `agents.md` 鼓励主动跨文件清理和不保兼容，与当前交易系统最小改动及独立架构评审冲突。
- 选择：以用户 2026-08-11 提供的 ADR/issue 驱动、一个 PR 一件事和不可改测试规则为准。
- 否掉了：合并两套互相矛盾的规则，或让旧 clean-cut 条款继续隐式扩大实现范围。
- 代价：发现的旁支问题必须另开 issue；部分修复速度会降低，但评审边界更清楚。
- 状态：用户直接指定；长期工作约定。
